# Key-estimate cache payload v1

`encode_key_cache` and `decode_key_cache` serialize disposable source-analysis results only. They are worker/control-side operations and never run in the audio callback. They do not edit a project or persist user corrections. `CacheStore` owns atomic file publication and the outer SHA-256 envelope; this inner payload uses FNV-1a 64 to catch accidental byte damage when the codec is used by itself. Neither checksum authenticates hostile content. The decoder validates every field and never returns a partial result.

The common `LDANLYS1` header is little-endian: format version `u16=1`, kind `u8=3`, reserved `u8=0`, exact total length `u32`, source-key length `u16`, reserved `u16=0`, reserved generation `u64=0`, sample rate `u32`, channel count `u32`, frame count `u64`, then 1–128 source-key bytes. The key body is presence `u8` (0/1), tonic pitch class `u8` (C=0 through B=11), mode `u8` (major=0/minor=1), confidence as IEEE-754 `f64`, related-key count `u8`, and each related key as tonic `u8`, mode `u8`, relation `u8`. A final little-endian `u64` FNV-1a covers all earlier bytes. Unknown is canonical: presence, tonic, mode, confidence and related-key count are zero. A known key requires positive finite confidence within [0,1] and exactly three relations in order: relative, dominant, subdominant, with the pitch classes and modes derived from the detected key. The maximum v1 payload is 44 + 128 + 21 + 8 = 201 bytes.

The source key supplied to this codec must be the canonical source-analysis `CacheKey` from ADR-0010: its descriptor includes immutable encoded-source digest/length/encoding and the key estimator's algorithm ID/version and settings. It is **not** just a path, source ID, project revision or caller-chosen label in production. The key-estimator unit fixtures use short labels; the cache contract fixtures use distinct `encoded-source-v1`/`v2` keys to prove stale-source rejection. Decode additionally compares verified sample rate, channels and frame count. Generation is intentionally absent from persisted bytes: a valid cache adopts the current request generation, after which the serialized install gate must rederive the current semantic key and claim the ticket once. A changed source or algorithm version must be a cache miss even if decoded metadata is unchanged.

The v1 format stores a suggestion and its compatibility metadata. It stores no manual override, confidence calibration, musical spelling, provenance of real-recording validation, or project key state. A change to key-estimator semantics, confidence interpretation, compatibility relations or bytes requires a new algorithm version in the semantic cache key; an incompatible payload layout also increments this payload version. Old entries are reconstructable and may be discarded.
