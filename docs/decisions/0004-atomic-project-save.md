# ADR-0004 — Generation-based atomic project saves

**Status:** Accepted; implemented (reviewed 20 October 2026). Generations, fsync/rename pointer publication, autosave and named revisions are in `src/persistence/store.cpp`. Every committed save also prunes old generations, keeping the 10 most recent valid ones plus those the pointers and named revisions reference. Amended by [ADR-0039](0039-background-editor-publication.md).
**Date:** 14 October 2026
**Requirements:** PRD §§8, 18, 21; FS-03 PM-03–PM-08.

## Context

A project contains a manifest and possibly multiple plugin-state blobs and media references. Replacing files in place can expose a mixed generation after a crash. A single rename is atomic for one directory entry, but durability also needs data and directory synchronization on Linux.

## Decision

Each project has `assets/` for durable original media, `state/generations/<id>/manifest.json` plus bounded state blobs for complete immutable generations, `state/CURRENT` for the last explicit save, `state/AUTOSAVE` for the latest autosave, `state/revisions/<id>` for named references, and disposable `cache/`. There is no second mutable top-level manifest. The human-readable generation manifest stores schema major/minor, generation and parent IDs, the monotone project revision, save kind, timing-format version and project rate through the canonical snapshot, typed asset references, and size/checksum references for blobs. Generation IDs are distinct from project revision IDs. Pointer files carry target generation and manifest checksum; display names never become path segments.

Save creates a new generation in a same-filesystem temporary directory. A single project writer stages and verifies managed assets first, then writes and flushes blobs and manifest, flushes the generation directory, validates its contents from disk, renames it to an immutable generation ID and flushes the generations directory. It then writes and flushes a temporary pointer, renames it over `CURRENT` or `AUTOSAVE`, and flushes the state directory. Autosave never advances `CURRENT`. Named revision pointers use the same durable-reference protocol. Save success is reported only after the final directory flush. If pointer rename succeeds but that flush fails, durability is indeterminate: retain edits in memory and report an uncertain save; reopen may find either complete generation. Migration first preserves a pre-upgrade generation and advances `CURRENT` only after validation.

After acquiring the sole writer lock on reopen, the store removes abandoned temporary save generations containing only known manifest files and abandoned regular temporary `CURRENT`/`AUTOSAVE` pointers. It leaves published generations, unknown stage contents and symlinks untouched, then flushes directories containing removals. Complete published generations without a pointer remain available to recovery.

Startup validates `CURRENT` and its target. If a readable pointer's target is corrupt, it follows predecessor references to identify validated recovery candidates and presents them for choice. If the pointer is unreadable, it offers validated complete generations for user choice rather than guessing by timestamp or silently marking one saved. An unpointed complete generation is recoverable but not automatically the explicit save. Recovery shows a valid `CURRENT` and `AUTOSAVE` separately.

Managed media additions use content identity and durable staging receipts before a generation can reference them. A two-phase import copies and verifies the source in a private `.stage-<random>` file on a worker without accessing the project writer or mutating the model. The sole writer verifies its current revision, reserved IDs, pinned directory and instance token before publication; cancellation or a dropped result removes the private stage. Reopening the sole writer scans a bounded number of entries and removes recognized abandoned regular staging files, without following symlinks or deleting published assets. A crash after linking a verified asset but before a manifest references it can leave an unreferenced durable asset. It is harmless, is not cache, and is retained because a recovery generation may need it. External links are typed references, never hidden dependencies. Project-managed paths are resolved relative to a held root directory descriptor, reject traversal and symlinks, and use `openat2` containment where available or component-wise `openat` with no-follow flags. A second writer opens read-only or receives an explicit conflict. Manifest/blob counts and sizes are bounded before allocation. Cache files are outside this transaction. The first manifest schema is strict, versioned, bounded UTF-8 JSON. Manifest and pointer integrity use SHA-256 through the system OpenSSL 3 `OpenSSL::Crypto` target, rather than an in-tree cryptographic implementation. OpenSSL 3 is [Apache-2.0 licensed](https://openssl-library.org/source/license/index.html); exact packaged version and transitive obligations remain in the component inventory. Syscall error mapping and the launch filesystem matrix remain G4 review items.

The default retention policy keeps the ten most recent complete generations plus every named revision. Pruning never removes the generation named by `CURRENT`, a named revision, the latest valid autosave offered for recovery, or an in-progress migration/backup. It runs off the audio thread only after a new generation is durable and validates references before deletion. Autosave and recovery metadata live in `state/`; no separate recovery data directory exists.

The writer now runs bounded pruning after the final pointer flush. It validates `CURRENT`, `AUTOSAVE` and named revision references first; ambiguous or damaged references prevent deletion. Complete generations are ordered by directory modification time with a stable name tie-break, and the ten newest plus every referenced generation are retained. Unknown or incomplete directories are left untouched. A pruning failure does not turn a durable save into a failed save: `SaveOutcome::maintenance_warning` carries the issue, and the application reports it. Recovery scans up to 8,192 directory entries and offers the newest 256 complete candidates within its existing decode budgets, so an older project with more than 1,024 generations still opens recovery choices. The explicit entry limit remains a resource bound, not a retention target. No in-progress migration/backup protocol is implemented yet; it must disable or extend pruning before it can publish generations.

An explicit recovery choice can revalidate and adopt a complete generation into its matching pointer kind. The writer checks the other valid pointer's project identity, writes a private pointer, renames it into place and flushes `state/`. A failure after pointer rename reports uncertain durability, as a normal save does. Choosing an autosave as the new explicit project state requires a separate user-directed save; a same-kind pointer repair does not silently promote it. The application chooser shows a newer validated autosave separately from the last explicit save and offers validated generation repair if a pointer is corrupt. Opening an autosave retains `CURRENT` and marks the session unsaved until the user saves explicitly.

## Alternatives considered

- Replace manifest and blobs in place: a crash can expose mixed state.
- Store autosave snapshots in a separate recovery tree: duplicates generation logic and leaves unclear which manifest is authoritative.
- Retain every generation forever: simplest recovery story but unbounded project growth.

## Consequences and evidence

Saves use more disk space until old generations are pruned under the stated retention policy. Fault injection and process-kill tests at asset, generation, pointer and pruning stages must leave either the old or new complete project recoverable; pointer-flush failure must report indeterminate durability. Relinking, collect-and-save, migration rollback, two-writer, symlink/path-swap and missing-state fixtures cover multi-file cases. The protocol follows Linux [rename](https://man7.org/linux/man-pages/man2/rename.2.html) and [fsync](https://man7.org/linux/man-pages/man2/fsync.2.html) semantics; filesystem qualification is still required.
