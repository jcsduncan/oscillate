# Qt Quick runtime and distribution inventory

**Status:** Development-build inventory; Ubuntu package and AppImage qualification open
**Observed:** 14 October 2026, Ubuntu 26.04 x86-64 development machine
**Scope:** `oscillate` only, under [ADR-0022](../decisions/0022-qt-quick-ui-direction.md) and implementation gate G8. This is dependency evidence, not a distribution approval or legal opinion.

## Observed build and runtime

The current Quick target in `apps/daw_quick/CMakeLists.txt` links `Qt6::Core`, `Qt6::Gui`, `Qt6::Qml`, `Qt6::Quick` and `Qt6::Widgets` dynamically. When `BUILD_TESTING=ON`, it **also links `Qt6::Test` into the executable** for smoke inputs. `Widgets` is a real dependency: `main.cpp` constructs `QApplication`, and `project_bridge.cpp` opens a project folder with `QFileDialog`. The bundled QML files import `QtQuick`; there is no source import of Quick Controls, Dialogs, Layouts or Multimedia. `qml.qrc` embeds the shell, welcome screen and four starter WAV files. The headless application and engine do not link Qt.

The native prototype now scans QML files named in `qml.qrc` and declares
[`qml6-module-qtquick`](https://packages.ubuntu.com/resolute/qml6-module-qtquick)
explicitly, since Qt's [QML deployment guidance](https://doc.qt.io/qt-6/qt-deploy-qml-imports.html)
notes that normal ELF dependency traversal cannot identify QML module imports.
This is a conservative package dependency; the local Qt build's resource-based
import resolution described below is not a clean-install test.

`readelf -d build/quick/apps/daw_quick/oscillate` reports direct `DT_NEEDED` entries for `libQt6Quick.so.6`, `libQt6Widgets.so.6`, `libQt6Qml.so.6`, `libQt6Gui.so.6`, `libQt6Core.so.6` and, in the current test-enabled build, `libQt6Test.so.6`. On this machine, `ldd` additionally resolves Qt QmlMeta, QmlModels, QmlWorkerScript, Network, OpenGL and DBus through those libraries. This is a transitive list for **this build**, not an exhaustive release SBOM. The executable also directly needs PipeWire and OpenSSL's `libcrypto.so.3`; those are outside this Qt inventory. A fresh 15 October inspection additionally found direct libsndfile and libsamplerate links from enabled codec/export options; see the [distribution review](distribution-sbom-review.md).

The binary has an absolute development `RUNPATH` into `~/.cache/<local-deps>/qt/usr/lib/x86_64-linux-gnu` and `/tmp/oscillate-jack-dev/root/usr/lib/x86_64-linux-gnu`. `ldd` resolves the five direct Qt libraries from the extracted local Qt tree but several transitive Qt libraries from `/usr/lib/x86_64-linux-gnu`. Both sets are currently Qt 6.10.2 Ubuntu builds. This mixed layout and absolute path are unsuitable as package evidence; the installed artifacts must be rebuilt and inspected independently.

An offscreen `--smoke --create` run passed with `QT_DEBUG_PLUGINS=1` and `QML_IMPORT_TRACE=1`. Its trace loaded the system `platforms/libqoffscreen.so` and `platforminputcontexts/libibusplatforminputcontextplugin.so`. QML resolved `QtQuick`, `QtQml`, `QtQml.Models` and `QtQml.WorkerScript` from `:/qt-project.org/imports/.../qmldir` resources. It did **not** load a Quick Controls or Dialogs plugin in this run. The installed `qml6-module-qtquick*` packages are absent on this machine; matching files are also present in the extracted local Qt package tree. Neither fact proves that an installed release build can omit QML packages: the package build, its Qt configuration and a clean-install runtime trace decide that.

The local Ubuntu package mapping includes `libqt6quick6`, `libqt6qml6`, `libqt6widgets6`, `libqt6gui6`, `libqt6core6t64` and transitive `libqt6qmlmeta6`, `libqt6qmlmodels6`, `libqt6qmlworkerscript6`, `libqt6network6`, `libqt6opengl6`, `libqt6dbus6`. `libqoffscreen.so` and `libqxcb.so` belong to `libqt6gui6`; `libqwayland.so` belongs to `libqt6waylandclient6`. The latter two were **located, not exercised** by the offscreen smoke. `qt6-wayland` is installed locally. The exact package dependency set must be derived from a built release artifact, not copied from this machine's installed package list.

## Open-source terms to verify for shipped files

Qt's [6.10 module licensing list](https://doc.qt.io/qt-6.10/licensing.html) distinguishes modules available under LGPLv3 from GPL-only modules; `Qt Qml Compiler`, `Qt Quick 3D`, `Qt Quick Timeline` and `Qt Wayland Compositor` are among its GPL-only list. The five ordinary direct modules used here each document an LGPLv3 option: [Core](https://doc.qt.io/qt-6.10/qtcore-index.html), [Gui](https://doc.qt.io/qt-6.10/qtgui-index.html), [Qml](https://doc.qt.io/qt-6.10/qtqml-index.html), [Quick](https://doc.qt.io/qt-6.10/qtquick-index.html) and [Widgets](https://doc.qt.io/qt-6.10/qtwidgets-index.html). [Qt Test](https://doc.qt.io/qt-6.10/qttest-index.html) also offers LGPLv3 but is linked only in the test-enabled configuration; Qt documents no binary compatibility guarantee for it. The build has no `Qt6::QmlCompiler` target or GPL-only Quick module import. This does not classify every transitive library or platform plugin; the final shipped-file inventory and its package copyright notices must do that. Qt also documents [third-party code within modules](https://doc.qt.io/qt-6.10/licensing.html#third-party-code-in-qt) and [per-release SBOM material](https://doc.qt.io/qt-6.10/licensing.html#software-bill-of-materials).

Qt's [open-source licensing FAQ](https://www.qt.io/faq/qt-open-source-licensing) and [obligations page](https://www.qt.io/development/open-source-lgpl-obligations) describe the LGPLv3 route: provide the applicable licence and prominent Qt-use notice; supply corresponding Qt source including modifications, or a project-controlled written offer; and let the user replace/relink the Qt libraries and run the result, with installation information. Dynamic linking is the intended route here. These are conditions to test against the **actual distributions**, including their launcher, library search path and update behaviour. An upstream download link alone is not the project-controlled source offer described by Qt. The project's own product licence and all other bundled dependencies remain separate decisions.

Qt's [deployment guidance](https://doc.qt.io/qt-6.10/deployment.html) says QML applications need their used QML modules and GUI applications need suitable platform plugins; [Linux deployment guidance](https://doc.qt.io/qt-6.10/linux-deployment.html) describes `xcb` and plugin paths. The current offscreen trace is insufficient to decide the Wayland/X11, image-format, input-method, accessibility or font plugin payload. Do not copy every file in the local Qt tree merely because it is present.

## Exact work remaining before distribution

1. **Build artifacts:** Produce a native Ubuntu package and AppImage from a clean release build, without this machine's absolute `RUNPATH`. Record exact Qt versions, package files, `DT_NEEDED` closure, plugins, QML resources/modules, fonts, translations and all transitive libraries actually shipped or required from Ubuntu. Resolve each file to its source package, licence and copyright notice in the component SBOM. A [local-only `.deb` prototype](ubuntu-package-prototype.md) now demonstrates the native packaging mechanism, but no release-candidate package or AppImage has been qualified.
2. **Native package:** Install on a clean Ubuntu 26.04 x86-64 target, with declared dependencies only. Run welcome, create/open, project-folder picker, playback and smoke on both Wayland and X11. Capture `QT_DEBUG_PLUGINS` and `QML_IMPORT_TRACE`; verify the QML module and QPA plugin closure, missing-file behaviour and absence of development paths.
3. **AppImage:** Run on a clean compatible Ubuntu target under Wayland and X11, first with normal libraries and then after replacing a bundled LGPL Qt shared library with an ABI-compatible modified build. Verify that the launcher, `RUNPATH`/`qt.conf`, mount permissions and update flow allow that substitution and that the modified library actually loads. Repeat for platform/QML plugins that the AppImage bundles and that are covered by LGPL terms. Document the exact replacement procedure for users.
4. **Native relinking check:** Replace a dynamically linked Qt library with an ABI-compatible modified version through the package-supported mechanism and demonstrate the app loads and runs it. Record the command, paths and result; package-manager upgrades must not silently remove the documented route.
5. **Notices and source:** Include complete applicable Qt/LGPL licence text, a prominent Qt-use notice, the exact corresponding Qt source or a controlled written offer, build modifications and user installation/relinking instructions in each distribution. Confirm package copyright files and Qt's SBOM against the exact shipped versions. Recheck licences whenever modules, Qt versions or plugins change.
6. **Plugin editor boundary:** Test the separate VST3 editor Wayland/X11 and generic-fallback spike before using it as a compatibility claim. This inventory covers the DAW shell, not embedded third-party plugin GUIs.

Reproduce the local observations with `readelf -d` and `ldd` on the Quick executable, then `QT_QPA_PLATFORM=offscreen QT_DEBUG_PLUGINS=1 QML_IMPORT_TRACE=1 oscillate --smoke --create <disposable-project-folder>`. These commands establish local load behaviour; they do not close the clean-package or LGPL replacement tests above.
