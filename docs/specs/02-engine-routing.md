# FS-02 — Engine, routing and devices

**Status:** Draft. **Dependencies:** timing contract, project graph description, processor API. **PRD:** §§7, 15, 22.

## Functional contract

- **ER-01** The callback renders the active immutable graph without waiting on UI, disk, background jobs, plugin scanning or model locks. Graph changes become audible at a block boundary after a complete new graph is ready.
- **ER-01a** A compatible live compressor setting update begins at a block boundary and blends its previous and new output gain over exactly 64 rendered frames. Detector and sidechain-filter state continue. A newer offered setting waits in the bounded mailbox until that transition finishes; the callback never waits. Acknowledgement means the new settings have begun applying, with their final gain reached after the transition. This reduces abrupt gain steps without claiming that all material or rapid edits are click-free.
- **ER-01b** A compatible live EQ setting update begins at a block boundary and moves each validated biquad coefficient to its new value over exactly 64 rendered frames. The filter delay state continues, and another offered update may start from the current intermediate coefficients at a later block boundary. The saved revision is acknowledged only after its final transition sample; a superseded revision need not be acknowledged. Processing uses fixed storage and does not allocate or wait in the callback. The transition limits an abrupt coefficient step but does not establish click-free output for every signal or setting pair.
- **ER-01c** A compatible live reverb wet/damping update begins at a block boundary and interpolates both controls over exactly 64 rendered frames. Comb and diffuser history continue, including tails already in flight. A newer offered update can begin from intermediate controls at a later block boundary. The saved revision is acknowledged after its final transition sample; a superseded revision need not be acknowledged. Decay and sample-rate changes still need a prepared graph transition because they change feedback and the published tail budget. The transition does not establish click-free output for all material.
- **ER-01d** One live EQ band may be appended to the end or removed at any position, within the one-to-eight-band limit, when the other bands are unchanged and the zero-latency native-chain mailbox is eligible. An added section starts at bypass with zero history and moves to its prepared coefficients over 64 rendered frames. A removed section moves to bypass while its state decays to zero, then fixed storage compacts; every surviving section retains its exact filter history. The saved revision stays pending until the final transition sample. An overlapping structural edit, ambiguous removal of identical saved bands, combined parameter edit, VST3/sidechain/limiter path, or unsupported chain fails visibly while the prior audible revision remains. A removed section's remaining tail is bounded to this 64-frame retirement; this is a reported limitation, not a guarantee that every removal is click-free.
- **ER-02** Track, group, return, send, sidechain and master routing form a directed acyclic signal graph. Cycles, missing destinations and unsupported channel layouts are rejected before activation with an actionable path description.
- **ER-02a** Main and send audio edges have independently set linear gain in the bounded range 0..4; unity is the default. Non-finite or out-of-range values are rejected before activation. The gain applies after delay compensation, so a graph handoff retains unscaled route history and uses the successor edge's gain. Sidechain bus semantics remain a separate input-bus contract.
- **ER-02b** Changing the static gain of an existing, unautomated send on a settled graph becomes audible at the next valid callback boundary without a transport hold when route identity, processors and timing remain unchanged. It reaches the new gain over at least 64 rendered frames while processor and compensation history continue. A send bound to automation, changed endpoint or ID, revision-sensitive processor, pending transition or other concurrent edit uses guarded publication with explicit saved-versus-audible status.
- **ER-03** Processor latency is accounted for on all parallel paths, including sends and sidechains. Bypass, removal and latency change cause safe recalculation. If required delay exceeds the configured budget, retain the old graph and report the path and limit.
- **ER-04** Transport start/stop/seek/loop obeys the shared sample position. MIDI and automation events scheduled inside a block reach their intended sample offsets where the processor supports them.
- **ER-04a** A pure Pause/Resume continues at the last completed project sample with the same transport generation and processor history. A paused seek changes the project sample and generation, invalidating source prefetch and processor history for the discontinuity. Pause or seek requested while a graph switch is published or waiting waits until the switch activates or fails; the transport must not restart against a boundary from an older generation. No edit holds the transport ([ADR-0094](../decisions/0094-primed-source-switching.md)).
- **ER-04b** A planned loop wrap may preserve processor history only after the next source iteration is primed and the control side requests the wrap at a callback boundary. The first wrapped block advances the transport generation for source and prefetch identity, retains a separate processing generation for sampler voices, effects, tails and PDC, and identifies the wrap explicitly. Later blocks in that iteration use the same two generations without repeating the boundary flag. An ordinary seek or device restart changes both generations and follows its own priming or recovery contract. The source event plan reads the new project position; held notes and effect tails continue according to processor state. Loop activation must not silently substitute an unprimed generation.
- **ER-05** PipeWire and JACK are v1 backends. The adapter requests the project's nominal rate. PipeWire may run its graph at another rate and convert the client stream; the engine continues at project rate and device status reports the actual graph rate and PipeWire-managed conversion. If the negotiated **client** stream rate differs from the project rate, playback enters an explicit error state, leaves project transport at the last completed sample, and offers output/rate correction before retry. A graph/server rate difference alone is not an error. JACK uses the server's fixed rate; a mismatch keeps playback stopped and offers instructions to restart JACK at the project rate or explicitly change the project rate. There is no engine-side whole-mix resampler. A disconnect transitions to silence without discarding edits, stops using invalid handles, and presents recovery/reselection. ALSA is an optional fallback.
- **ER-05a** A JACK server-shutdown callback only closes the playback gate and records disconnection. Control-side teardown closes the client outside that callback and does not try to deactivate a client after server shutdown. A zero-frame process callback leaves output state and transport unchanged.
- **ER-06** A failed graph build cannot corrupt the project or replace the last valid audio graph. A plugin process fault may bypass or mute when recoverable; a fatal in-process fault is outside hard containment guarantees.
- **ER-07** At 48 kHz, both 64- and 128-sample buffers qualify against the 32-track workload on the approved reference machine. The standard run targets zero xruns. Approximately 100 tracks is a design goal, not a launch gate.
- **ER-08** Topology-only edits preserve compatible processor instances and their DSP history, including delays, reverbs and plugin tails. Replaced processors use a prepared state and a bounded, reported transition policy; a graph edit must not silently reset a continuing processor.
- **ER-08a** A decay change to the last enabled native reverb stage on an otherwise unchanged audio, group or return path prepares a new reverb off callback and switches it in live at a block boundary. Earlier native stages retain their processor instances and history; the old reverb alone receives zero input and drains its bounded tail through the same routing node while the new reverb handles continuing signal. A second decay change cannot replace an unfinished predecessor tail; its saved revision remains inactive with a retry path. The Quick decay dial commits one deferred drag on release. This does not permit another simultaneous chain edit, a later effect stage, changed latency, or a VST3/sidechain path in the same handoff.
- **ER-08b** The same selected-stage tail handoff applies to a final master reverb after unchanged, zero-latency native EQ and compressor stages. The project edit must change only the master reverb settings; all other saved project fields stay fixed. Earlier master processor instances and history survive the switch. Master chains with a later stage, limiter latency or VST3 do not use this handoff.
- **ER-08c** A built-in synth engine selection, alone or with other edits, prepares a replacement source bank off callback against the exact saved revision ([ADR-0098](../decisions/0098-whole-replacement-switches.md)). The revision-matched source and graph take over together at the first block the source fills completely after any track the edit drops has faded out, without stopping transport, also inside an active loop; unchanged insert histories remain owned by the graph. From that block, the old synth releases its held notes and rings out for its declared tail beside the new one, which starts with its next note. If preparation, priming or graph publication fails, the saved choice remains inactive, the old source keeps playing, and the failure is visible. This is not a held-note morph or note chase.
- **ER-09** The model revision and active graph revision are independently visible. Each engine-affecting edit is pending, active or failed. A failed graph build preserves the edit and old valid playback, identifies the failed change and offers retry or undo.
- **ER-10** PDC delay history is reused where compatible and new delays are primed before activation. Parallel paths stay aligned at a graph switch. Dynamic plugin latency changes enter a safe pending state; over-budget or unprimeable paths use a reported hold/bypass/mute policy rather than known-misaligned mixing.
- **ER-11** The callback never opens or reads a file or invokes a media decoder, source resampler or stretch worker. A media prefetch service fills preallocated per-clip rings. Transport start and unanticipated seek enter a visible `priming` state: control-side work waits up to a measured bounded deadline for minimum ring occupancy; on timeout playback stays stopped/paused with a diagnostic. Planned loop wraps are prefetched ahead and tagged for the next iteration. Only a ring shortfall after transport enters steady-state playback counts as a prefetch underrun: the callback emits silence for the missing segment, increments a bounded counter and reports the affected clip and interval off-thread; it never waits. Per-clip callback events enter a bounded SPSC queue. Queue overflow increments a separate drop counter, while the total underrun counter remains available. The status reader reports the clip ID, generation and missing source-frame interval from drained events.

## Component contract

The graph builder runs off the callback. Each node declares input/output buses, channel layouts, maximum block size, scratch needs, latency and event capabilities. Construction preallocates graph buffers and new compensation lines; mutable processor runtime and compatible delay histories remain separately owned across revisions. A transition manifest names reused, replaced, priming, draining and retiring objects by stable ID. The callback owns no project pointers, processes one live graph generation per block and never concurrently processes a reused instance in two live graphs. A reclamation test proves plans and runtime objects cannot be freed while in use. Meter values pass to the UI through bounded, lossy snapshots; dropping meter frames is acceptable, dropping commands is reported.

The media prefetch contract carries clip ID, generation, source position, rate, loop/seek state and bounded ring occupancy. The control side sets a measured minimum occupancy and bounded priming deadline; planned loop generations can coexist with current playback frames, while an unanticipated seek discards obsolete frames. The callback consumes only ready frames; worker priority follows transport proximity. The device adapter contract carries requested client rate, actual graph/server rate, conversion status, block size, device lifecycle events and xrun evidence where the backend exposes it. An unavailable per-stream xrun count remains explicitly unknown; PipeWire qualification records stream and driver error-counter deltas alongside application render failures and source underruns, identifying each metric separately. Adapter error handlers cannot directly edit project state. The callback has a documented worst-case path for silence and device loss. The PDC budget, stereo channel-layout contract and reference plugin set are gates before ER-03/07 are accepted. See the [PipeWire stream API](https://docs.pipewire.org/group__pw__stream.html) and [pw-top counter definitions](https://docs.pipewire.org/page_man_pw-top_1.html).

The live EQ band-count slice passes native runtime, routed control and Quick bridge contracts at 64 and 128 frames, including exact survivor-history continuity, pending-to-active acknowledgement, back-to-back edit rejection, ambiguous-band failure status, undo and zero counted callback allocations. The uninstrumented Release EQ microbenchmark on Intel Core i7-10700K with GCC 15.2.0 at 48 kHz (20,000 warm stereo blocks, five-run median) measured 2.641 µs per 64-frame block and 5.205 µs per 128-frame block for eight bands. The prior same-host result was 2.55/5.14 µs; host load was uncontrolled, so this comparison is indicative rather than a regression gate. It is not a whole-graph or device-xrun result.

Unit coverage is necessary but cannot substitute for callback timing, real device and reference workload tests.

The engine-only bounded-gain slice passed GCC and Clang route contracts, ASan/UBSan, TSan publisher contracts, and 98% combined line coverage of `routing_latency.cpp` and `routed_mixer.cpp` (208/211 executable lines). The callback allocation fixture observed zero allocations. On Intel Core i7-10700K with GCC 15.2.0 Release at 48 kHz, 20,000 measured blocks of 32 stereo routes with alternating unity/half gain took 16.84 µs per 64-frame block and 32.00 µs per 128-frame block. This is a route microbenchmark, not project routing integration or the 32-track plugin/device qualification.

The shared routing module translates validated project main outputs and sends into engine node/edge IDs on the control side. One registry belongs to one open project session. It preserves full 128-bit project IDs in maps and allocates distinct 64-bit engine IDs without truncation, including after a remove/re-add; failed plans do not consume IDs. The master is node 1. Source bindings name track ID, engine node ID and topological source slot. Track order in the manifest cannot change this mapping. The compiler checks routing limits, destinations, gains and cycles, and calls the engine latency planner with an explicit caller-supplied compensation limit. Route compilation defaults to fail closed for saved VST3 inserts. The route compiler validates at most three VST3 receipts per track, including at most one source and two following effects on an instrument track. It can map two VST3 instrument sources to independent track nodes, including one verified VST3 effect on each path, and rejects a third source. Its four-receipt project-wide limit is a provisional development bound, not a measured host budget or release qualification. Routed live playback permits three serial verified VST3 effects on one audio track, two effects on separate audio tracks, one MIDI instrument with up to two serial verified effects on its own track, or exactly two direct VST3 instrument tracks with one verified VST3 effect each. These bounded layouts require matching verified bindings and initial latencies; broader combinations remain unavailable. The live application composes the terminal master processor and passes its exact latency into the engine's audible graph planner. A saved sidechain send names one enabled native compressor or VST3 effect slot and uses an aligned detector edge separate from audible sends. A VST3 target requires an exact saved-slot receipt and a successfully activated stereo auxiliary input bus; unsupported plugins fail before graph publication and leave the previous audible revision intact. Instrument sidechain targets remain unsupported. A successful route plan proves only routing topology and source-slot mapping: it is not an audible graph, a PDC qualification, or permission to bypass the active-versus-model revision gate.

The `compile_bound` entry point matches each enabled saved VST3 source or effect to an exact plugin, track, role and effect-slot receipt carrying its initial latency. It derives serial stage order from saved effects, retains the existing single-source native/mixed limits, and compiles independent per-track arrivals into one latency plan. Its two-source shape requires bare paths; source-state replacement, live attachment and multi-source export remain unsupported until their separate runtime and render contracts are qualified. It also validates ordered native chains and sums source and chain latency on existing single-source paths; live and offline consumers must prepare and attach those processors before claiming a route is audible. It rejects missing, duplicate, orphaned, ambiguous mixed and over-budget bindings without consuming route IDs. The existing single-insert `compile` entry point retains its fail-closed behaviour. Routed live playback owns each verified runtime and fault probe separately, maps each one to its source node, and reuses it across compatible route edits. The routed live path permits adding, removing and changing an isolated zero-latency master reverb at an acknowledged block boundary. A removed or replaced reverb drains its bounded predecessor tail. Sole master EQ and compressor transitions follow the bounded rule below. It also permits adding one prepared zero-latency native EQ, compressor or reverb to an empty audio or bus path when no other native or VST3 path is active; the addition becomes audible at the switching block without replacing existing processors. A compatible coefficient edit to exactly one enabled native EQ or compressor slot in an unchanged, zero-latency audio, group or return chain is prepared off callback and adopted from a bounded mailbox at a block boundary. The chain cannot include a VST3 slot or sidechain target. The processor retains its filter or detector history; the edit remains pending until the callback acknowledges it, with no held silent block. Chain, routing and latency changes switch live (ADR-0049, ADR-0050). Track, tempo, meter, media and instrument changes switch with a whole replacement source at a primed block (ADR-0098). A VST3 instrument takes MIDI and tempo edits as a plan, a replaced one releases its notes, and a tempo change prepares VST3 effects afresh (ADR-0101). A change of VST3 parameter automation is refused while playing. An edit no live path takes is refused at once (ADR-0094), and any failed model revision stays visibly distinct from the prior audible graph. A VST3 effect whose new state changes its latency is a new instance that switches live, with delay compensation moving to the new latency (ADR-0101).

The native reverb runtime has a separate bounded mailbox for wet and damping updates. It preserves comb and diffuser history when adopting a compatible value at a block boundary. An enabled native reverb slot in an unchanged, zero-latency audio, group or return chain without VST3 slots or sidechain targets can publish such saved settings while routed playback continues; the revision stays pending until callback acknowledgement. Decay and sample-rate changes alter feedback or the published tail budget and require a prepared graph transition with explicit tail accounting. The track device editor permits a deferred decay gesture when the reverb is the last stage of the native chain as described in ER-08a. The master chain uses the same selected-stage rule in ER-08b; reverb creation or removal switches live like any other chain edit (ADR-0050).

The same compatible native parameter mailbox contract also applies to an instrument track with a verified built-in or VST3 source and an unchanged native chain. The source and its processor state survive the edit. An enabled native limiter on an unchanged audio, instrument, group or return chain may adopt prepared ceiling and release settings at a block boundary while playback continues. The bounded mailbox keeps its running peak, gain and lookahead delay state. The saved revision remains pending until callback acknowledgement. This path requires the same lookahead duration and exact prepared latency; changing lookahead or topology switches live with ADR-0049's latency handover, and a sample-rate change needs a restart. The track device editor enables ceiling and release during playback and disables lookahead. A chain with nonzero limiter latency does not gain live EQ, compressor or reverb edits through this contract.

An unchanged zero-latency master native chain accepts prepared EQ, compressor, and reverb parameter edits through the same bounded block-boundary mailboxes used by tracks. EQ band count may change by one append or removal under ER-01d; changing a band's filter kind or shape prepares coefficients off callback and uses the same 64-sample transition while preserving filter history. Reverb decay stays fixed. A master chain containing a limiter permits ceiling/release edits on that limiter, but holds earlier EQ, compressor and reverb edits. Pending and failed saved revisions remain distinct from the audible graph. The routed live master-limiter path uses the already prepared Ceiling true-peak limiter ([ADR-0117](../decisions/0117-ceiling-mastering-limiter.md)) as the final master stage. Its lookahead is the master **engine-stream output** latency in project-rate frames: stream frame `N + L` carries project frame `N`, before any additional device latency. All parallel routes converge before this stage, so the limiter does not consume the edge PDC budget or change their alignment. Live output deliberately does not discard the first `L` delayed frames; offline export discards those leading frames at its writer boundary. An uninterrupted stream requires `L` silence-fed frames after its last source frame to emit the tail. Quick Stop requests a bounded silent-input drain for the prepared limiter lookahead before joining the device; a 250 ms worker deadline or output/source failure reports an incomplete drain rather than claiming success. An unrelated live route edit reuses the same limiter runtime and delayed samples. Ceiling and release changes with the same lookahead use the bounded prepared-settings mailbox, preserve the running delay and gain state, and become active after callback acknowledgement. Enabling, disabling or changing lookahead while running switches live with ADR-0049's latency handover. This path is not a general live PDC or dynamic processor-latency solution.

## Sole master EQ and compressor handoff

At a live switch, a sole zero-latency master EQ or compressor can be
added, bypassed, re-enabled or removed. A retiring EQ drains a bounded filter
tail into the dry or newly prepared successor. A compressor detector has no
audible zero-input release tail. Publication remains pending until callback
acknowledgement. Multi-stage master chain replacements and limiter lookahead
changes retain their explicit guarded status.

An isolated removal of the last stage from a two-stage, zero-latency native
track, bus or master chain reuses the earlier runtime. Only the removed stage
receives zero input and drains its bounded tail into the successor route.
Removing an earlier stage, changing latency, a sidechain target or a VST3
stage does not use this handoff.

An isolated addition of a second zero-latency native stage at the end of a
one-stage audio, group, return or master path retains the first stage's runtime
and prepares the new stage off the callback. Bypassing that final stage drains
only its bounded tail; re-enabling it prepares a fresh stage while preserving
the prefix. Publication names the exact quiescent predecessor owner and
rejects a wrong owner or an unfinished predecessor drain. No old stage is
processed twice. The master records a conservative combined tail bound. An
earlier-stage insertion, a latency change, a sidechain target or a VST3 stage
remains guarded.

For a verified instrument source with one native stage, the same isolated
final-stage addition keeps the source runtime and first native stage. The
successor serial owner is prepared off the callback and names the old serial
owner as its quiescent handoff predecessor. It must process the source exactly
once after publication. Bypassing or removing the final stage
uses a replacement serial owner with the same source and prefix stage. The old
serial owner is pinned while only its retired final stage receives zero-input
tail blocks; source notes and DSP history continue once per live block.
Re-enabling that saved final stage prepares a new stage and uses a quiescent
serial-owner handoff. Earlier-stage changes still require a separate contract.

The same source-owner handoff applies when an eligible playing instrument has
no native stage and gains its first zero-latency EQ, compressor or reverb.
Only an isolated effect change is admitted: the instrument source, routing,
other tracks and timing stay fixed. A verified VST3 source keeps its running
processor instance. Bypass
or removal of the sole native stage returns to the original source path, and
only the retired stage receives zero-input tail blocks. Re-enabling that stage
prepares a new native runtime. At 64- and 128-frame boundaries, tests must
confirm one source process per block, correct dry output and retired tails,
and zero callback allocations.
