# Headless VST3 instrument WAV export slice

The exporter consumes the same insert projection as ordinary export.
It requires one unambiguous VST3 instrument source. The mixed managed-WAV path
also accepts one enabled VST3 audio effect on a separate audio track; other
track or bus effects fail before opening output. A saved missing instrument
flag does not bypass the mandatory fresh scan and exact receipt check.

Both the fresh render host and the independent tail probe request VST3 offline
I/O and processing mode. A plugin that rejects this mode fails export visibly
before publication. The synthetic fixture refuses real-time mode during the
offline contract test. This checks mode propagation, not the quality or
compatibility of third-party offline rendering.

`oscillate::vst3_instrument_export` is an optional target in scanner-enabled builds. It renders one saved VST3 instrument source through the existing routed playback graph to a master or one processed source stem. The graph runs at the project rate; the [shared output stage](vst3-output-formats.md) writes WAV float32/PCM24/PCM16, FLAC or MP3 at a selected output rate. The stem and master are identical for this one-source slice, including saved main and send routes. It uses the shared MIDI event compiler, tempo map, route planner and send-gain evaluator. No live plugin instance or project state is changed.

The caller must hold `StoppedExportAuthority`. Each render invokes the out-of-process scanner anew on the supplied bundle path, compares its canonical bundle path, binary hash and class identity with saved project intent, then asks the verified host for a tail after restoring saved component state and activating a separate probe instance. A relocated bundle requires a separate explicit relink workflow; this API does not silently substitute it. Export rejects absent, changed, quarantined or incompatible plugins before opening output. The render uses a fresh plugin instance and 128-frame graph blocks. A process fault discards the unfinished WAV temporary file; a successful render atomically publishes through `WavWriter`.

This slice requires a finite plugin-reported tail of at most ten seconds and drains that many frames after the final MIDI note-off. Infinite, unavailable or larger tails fail visibly. Third-party tail reports can be wrong or can change during processing; this fixture validates the contract, not arbitrary third-party tail correctness. The synthetic instrument reports and produces an eight-frame tail in the export test. Compatibility testing must compare real plugin output to its reported tail before treating it as complete.

The one-source API boundaries are one instrument source track, optional empty group/return buses and saved send routes, bounded stepped or gradual tempo accepted by the provider, no other audio source, track inserts, master effects with latency, or loudness report. Instrument plugins with nonzero latency are rejected until their offline alignment is qualified. These constraints avoid publishing an apparently complete render with truncated effects or wrong timing. The general offline master/stem renderer still rejects VST3 tracks; this opt-in API is a separate headless slice, not a release gate.

Local fixture checks cover save/reopen, main-plus-return sum, MIDI onset, finite tail, byte-identical repeat and processed stem, saved binary mismatch, infinite/oversized tail and process-fault publication. The synthetic fixture is not evidence of broad VST3 compatibility. See `tests/application/vst3/vst3_instrument_export_tests.cpp` and `tests/plugins/bundle_loader/instrument_plugin.cpp`.

## Mixed managed-WAV slice

The optional target also exposes `render_vst3_mixed_wav_master` and `render_vst3_mixed_wav_stem`. They admit one to eight additional plain audio tracks, each with one to 32 nonoverlapping clips, from at most 64 distinct referenced managed WAV sources. Each referenced saved source is fully verified once by `ProjectStore::open_managed_source` and held by a fresh pinned source-rate reader for the render; multiple clips can reuse that reader at different trim offsets. The exporter resolves each clip through the shared tempo map, sorts a private prepared view by sample start, then rejects overlap. Saved clip order does not change the result. Source trim remains in original source-frame coordinates; the shared `source_rate_frame_count` maps each endpoint to project frames. Placement duration must equal the converted endpoint difference. The existing one-hour output bound applies to every clip. Clip/track automation, audio inserts and MIDI content on audio tracks fail explicitly; warped clips render through `processing::OfflineWarpClip`.

Master rendering combines all verified audio tracks and the VST3 instrument in the existing route graph. A selected stem feeds only its chosen track through saved main and send routes, leaving other audio-track slots silent. An audio stem uses a temporary in-memory render snapshot without the instrument insert or MIDI clips; the saved project remains unchanged. The instrument stem leaves every audio source span silent. All files have the same timeline length, ending after the latest audio clip or finite reported instrument tail, plus any enabled effect drain. Each render freshly scans each active plugin and uses exact receipts for its new graph. Each WAV has independent atomic publication; a stem directory remains later work.

One enabled VST3 effect on one separate audio track is supported in this mixed path. The stopped exporter independently rescans and checks its saved bundle, binary hash and class, restores a fresh instance, validates its finite reported tail and latency, and binds it in offline processing mode alongside the instrument. The experimental effect compensation cap is 8,192 frames. It renders an extra graph-latency interval, then strips that prefix from the published WAV so instrument, dry tracks and wet track retain project-time alignment. The finite effect tail is added conservatively to the common master and stem extent. An effect process fault discards the partial WAV; a changed binary or unsupported mixed insert chain fails before publication. Native master inserts together with this effect, plugin parameter references, effect bypass and further effect slots remain outside the bounded contract. Source preparation still calls `ProjectStore::open_managed_source` before opening output, so linked external media is rejected until its separate reader and verification contract is implemented. The Qt Quick master action already dispatches projects with an instrument and managed audio through this mixed exporter, so it does not omit the effect.

The original mixed fixture saves and reopens a 12-frame PCM source, renders its trimmed frames 2–9 at project frames 260–267, and checks the independently calculated direct-plus-return contribution in each channel. The expanded fixture reopens two audio tracks and five clips from two sources, including a shared source at different offsets, unsorted saved clip order, gaps, simultaneous tracks and a clip crossing the 128-frame block boundary. It checks a frame-by-frame independent sample oracle for master and three stems, common 274-frame duration, finite instrument tail and byte-identical repeat. The simultaneous plugin fixture saves and reopens an instrument plus a separate effect, checks independent wet/dry master and two-stem samples, 96-frame latency alignment, an eight-frame effect tail, repeat bytes, changed binary rejection, process-fault cleanup and over-budget latency refusal. A separate 44.1→48 kHz fixture saves and reopens source-coordinate trims across the 128-frame boundary, then checks rounded duration, physical pitch, master/stem isolation and byte-identical repeat. It rejects mismatched placement, collapsed source trim and stale identity without replacing an existing output; converter-OFF builds reject the differing rate before publication. Other rejection tests cover stretched placement, overlap, the audio-track bound, missing/damaged managed bytes and plugin process faults. These are bounded headless fixture results, not arbitrary third-party plugin qualification. See `tests/application/vst3/vst3_mixed_export_tests.cpp`.

The source-rate path uses the same optional worker-only `SourceRateReader` and libsamplerate `SRC_SINC_MEDIUM_QUALITY` implementation as routed playback and ordinary offline export. It reads at most 128 project frames per clip per render block, keeps at most 64 pinned verified readers and does not cache a converted file. With the converter enabled, each reader owns a fixed 16,384-frame stereo decoded/input/output window, about 384 KiB or about 24 MiB at the 64-source limit, excluding decoder and route buffers. The `OSCILLATE_BUILD_SOURCE_RESAMPLER` option remains off by default; differing rates fail before the WAV writer in that build. Enabled package artifacts need the inventoried libsamplerate runtime and BSD-2-Clause notice. This does not qualify packaging or a general output-rate converter.

## Built-in master effects

The stopped exporter accepts active built-in master effects in their saved order, with saved bypass respected. It uses the same saved controls as live playback, and each effect's bounded tail (`EffectEngine::tail_frames`) is appended after the later of the final managed audio clip and the instrument's finite reported tail. The complete output, including effect drains, remains within the one-hour cap. Selected processed stems retain the common master duration and each gets a fresh, isolated master runtime. Nonlinear effects such as compressors mean processed stems are not generally additive to the master. A master effect with latency (such as a lookahead limiter), an enabled VST3 master slot or invalid master controls fail before WAV publication. A bypassed VST3 master slot remains saved and does not affect the render.

The local fixtures check exact output extent, analytic EQ first impulse and compressor first-frame gain, and calculated first wet comb/diffuser impulses from both the VST3 instrument and a one-frame managed audio clip. They also check source-stem isolation, linear reverb master/stem summation, nonlinear compressor nonadditivity, saved order against a compressor-then-EQ impulse oracle, bypass against the corresponding single-processor renders, byte-identical repeats, the fully dry case, rejection at the one-hour output bound, and unchanged output after validation or plugin-process faults. This remains a 128-frame headless route; 64-frame VST3 hosting and third-party tail accuracy are separate gates.

Local CPU screen, 15 October 2026: on an Intel Core i7-10700K (16 logical CPUs), GCC 15.2.0 `Release` with the synthetic VST3 fixture at 48 kHz and 128-frame graph blocks, 20 repeated mixed fixture runs consumed 1.06 s user CPU and 0.69 s system CPU in 1.74 s wall time (11,656 KB maximum resident set). The fixture includes project creation, verification, scanning and WAV publication as well as EQ, compressor and reverb rendering, so this is a regression smoke measurement, not a DSP-only throughput or callback allocation qualification. The fixed 128-frame exporter has no 64-frame mode.

With the source-rate fixture added, the same machine/compiler and a converter-enabled `Release` build completed 20 mixed fixture runs in 1.43 s user CPU, 1.10 s system CPU and 9.22 s wall time (12,416 KB maximum resident set). Wall time includes durable file publication and local storage contention. The separate five-second `SourceRateReader` 48→44.1 kHz worker benchmark measured median 0.596 s at 64-frame reads and 0.310 s at 128-frame reads over five repetitions. This is a CPU screen for the existing converter, not an allocation proof or a reference-hardware underrun qualification. Focused GCC coverage measured 320/366 lines (87%) in the stopped VST3 exporter and 112/121 (92%) in the reused source-rate reader; remaining exporter misses include unrelated fault branches.
